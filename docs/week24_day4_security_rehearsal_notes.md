## 3. STIX 2.1 Bundle Structure

### 3.1 Bundle Object Hierarchy

Every TAXII objects response returns a fully-structured STIX 2.1 bundle:

```
bundle (type: "bundle", spec_version: "2.1")
  ├── identity         (PhantomNet Sentinel — singleton anchor)
  ├── marking-definition  (TLP:WHITE / GREEN / AMBER / RED)
  ├── attack-pattern   (MITRE ATT&CK technique, kill_chain_phases, external_refs)
  ├── indicator[]      (one per IOC: IP, domain, URL, md5, sha256, email)
  └── relationship[]   (indicator "indicates" attack-pattern)
```

### 3.2 Key STIX 2.1 Compliance Points

- All object IDs are **deterministic uuid5** — same technique/IOC = same STIX ID, enabling deduplication
- `spec_version: "2.1"` on every SDO (required per OASIS STIX 2.1 §3.1)
- `attack-pattern` includes MITRE ATT&CK `external_references` with `source_name: "mitre-attack"`, `external_id`, and full URL
- `kill_chain_phases` derived from tactic name (`"Credential Access"` → `"credential-access"`)
- TLP marking definitions use singleton STIX library objects (no custom IDs needed)
- `object_refs` in Report SDO never empty — Identity anchor always included
- Validated by `stix2.parse()` Python SDK — 100% OASIS schema compliant (172 tests)

### 3.3 IOC Pattern Types Supported

| IOC Type | STIX 2.1 Pattern |
|---|---|
| ip / ipv4 | `[ipv4-addr:value = 'x.x.x.x']` |
| ipv6 | `[ipv6-addr:value = '...']` |
| domain | `[domain-name:value = 'evil.example.com']` |
| url | `[url:value = 'http://...']` |
| md5 | `[file:hashes.MD5 = '...']` |
| sha256 | `[file:hashes.'SHA-256' = '...']` |
| sha1 | `[file:hashes.'SHA-1' = '...']` |
| email | `[email-addr:value = 'attacker@evil.com']` |

## 4. Last-Minute Security Fixes Applied

### Fix 1 — Port 0 Snort Rule Generation Bug

**Location:** `backend/sentinel/rule_generator.py` — `validate_snort_rule_inputs()`

**Problem:** An explicit `if dst_port == 0` early-return rejection block incorrectly blocked port 0 from generating a valid Snort rule. This contradicted `validate_port()` which correctly returns `True` for any port in `0–65535`. The bug caused `generate_snort_rule("any", 0, ...)` to return an error dict instead of a valid rule string.

**Fix:** Removed the erroneous port-0 rejection block. Port validation is already enforced by `validate_port()`. Test updated to assert the result is a `str` containing `" 0 ("`.

**Impact:** Previously failed test `TestSnortRulePriority::test_port_zero_generates_valid_rule` now PASSES.
